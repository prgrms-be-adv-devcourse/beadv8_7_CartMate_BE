# 정산(Payout) 흐름 정리

판매자에게 판매 대금을 언제, 얼마를, 어떻게 지급하는지 한 번에 이해할 수 있도록 정리한 문서입니다.

## 1. 한 줄 요약

> 구매자가 결제한 돈은 **홀딩(에스크로)** 에 묶여 있다가, 구매확정된 건은 **다음 달 15일**에 **수수료 3%를 뗀 금액**이 판매자 지갑으로 입금된다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 홀딩 (`holding`) | 구매자가 결제한 돈을 판매자에게 주기 전까지 묶어 두는 곳. **구매자의 결제 한 건당 하나**이고, 주문 전체(여러 판매자의 여러 상품)를 담는다. 공동구매는 참가자마다 하나씩 생긴다. |
| 정산 (`payout`) | 판매자가 받을 돈의 기록. **주문 상품 하나당 한 건**이다. |
| 판매 금액 (`salesAmount`) | 단가 x 수량. 구매자가 낸 금액. |
| 수수료 (`feeAmount`) | 판매 금액의 **3%** (원 단위 미만 내림). 플랫폼이 가져간다. |
| 정산금 (`payoutAmount`) | 판매 금액 - 수수료. 판매자가 실제로 받는 금액. |
| 플랫폼 지갑 | 수수료가 쌓이는 지갑. 설정으로 지정한 **관리자 회원의 지갑**이다. |

## 3. 전체 흐름

```
[판매자 등록]
  member ──SellerRegisteredEvent──▶ payout: 판매자 ID ↔ 회원 ID 복제 (payout_seller)

[구매확정]  구매자가 누르거나, 배송완료 7일 뒤 자동 확정
  delivery ──DeliveryConfirmedEvent──▶ payout: 상품별 정산(PENDING) 생성
                                        · 수수료 3% 계산
                                        · 지급 예정일 = 구매확정 다음 달 15일

[지급]  매일 00:10 배치(Spring Batch) 실행 → 지급 예정일이 지난 PENDING 정산을 한 건씩 처리
  payout ──WalletSettlementPort──▶ wallet
                                    ① 홀딩에서 판매 금액을 꺼냄 (구매자별 홀딩 남은 금액 비율)
                                    ② 판매자 지갑에 정산금 입금   (거래 내역: SETTLEMENT)
                                    ③ 플랫폼 지갑에 수수료 입금   (거래 내역: FEE)
  payout: 정산 상태를 COMPLETED로 변경, 지급 시각 기록
```

- ①②③과 `COMPLETED` 처리는 **한 트랜잭션**입니다. 하나라도 실패하면 모두 롤백되고, 정산은 `PENDING`으로 남아 **다음 날 배치가 다시 시도**합니다.
- 구매확정 이벤트에서 정산을 만들 때도 같은 트랜잭션이라, 정산 생성이 실패하면 구매확정도 롤백됩니다.

## 4. 돈 계산 예시

판매 금액 10,000원 상품 한 건을 구매자 A(6,000원), B(4,000원)가 나눠 결제한 공동구매 주문일 때:

```
수수료  = 10,000 x 3% = 300원
정산금  = 10,000 - 300 = 9,700원

홀딩에서 꺼냄: A의 홀딩에서 6,000원, B의 홀딩에서 4,000원  (남은 금액 비율, 합계 10,000원)
입금:          판매자 지갑 +9,700원 / 플랫폼 지갑 +300원      (합계 10,000원)
```

- **수수료는 구매자별로 따로 떼지 않습니다.** 정산을 만들 때 상품 단위로 한 번만 계산하고(내림), 그 금액을 그대로 판매자 몫과 플랫폼 몫으로 나눕니다.
- 구매자별로 나누는 것은 **홀딩에서 꺼내는 금액뿐**입니다. 어느 구매자의 홀딩에서 얼마를 썼는지 기록하고, 환불 한도를 맞추기 위한 장부입니다.

### 왜 구매자별로 수수료를 따로 계산하지 않나?

구매자별로 3%를 따로 계산하면 **원 단위 반올림 때문에 합계가 총액 기준 값과 어긋나기** 때문입니다.

판매 금액 9,999원을 구매자 3명이 3,333원씩 낸 경우:

| 계산 방식 | 구매자당 수수료 | 합계 | 총액 기준(`9,999 x 3%`, 내림 = 299원)과 비교 |
|---|---|---|---|
| 총액으로 한 번만 계산 (현재) | - | **299원** | 기준값 그대로 |
| 구매자별 내림 | `3,333 x 3% = 99.99` → 99원 | 99 x 3 = **297원** | 2원 부족 (3%보다 덜 뗌) |
| 구매자별 반올림 | 99.99 → 100원 | 100 x 3 = **300원** | 1원 초과 (3%보다 더 뗌) |

- 어긋나면 정산 기록(`payout.fee_amount`), 플랫폼 지갑에 들어간 수수료, 판매자 정산금의 합계가 서로 맞지 않게 됩니다. 판매자 화면에 보이는 수수료와 실제 입금액이 달라질 수도 있습니다.
- 반올림해서 3%를 넘기면 약정보다 더 떼는 셈이라 판매자에게 불리해집니다. (에러가 나는 것은 아니고, 금액이 틀어지는 문제입니다.)
- 그래서 수수료 숫자는 **`Payout` 한 곳에서만 정하고**, 그 값을 그대로 씁니다. 구매자 수가 몇 명이든 `정산금 + 수수료 = 판매 금액`이 항상 정확히 맞습니다.
- 대신 홀딩에서 꺼내는 금액은 구매자별로 나누되, 합계가 판매 금액과 정확히 같아지도록 남는 원을 맞춰 줍니다.
- 나누어떨어지지 않으면 남는 원을 남은 금액이 큰 홀딩부터 1원씩 더해서 합계를 맞춥니다.
- 정산금이 0원이면(0원 상품) 입금 없이 바로 `COMPLETED` 처리합니다.

## 5. 테이블

| 모듈 | 테이블 | 역할 |
|---|---|---|
| payout | `payout` | 정산 한 건(상품 단위): 판매 금액, 수수료, 정산금, 상태, 확정 시각, 지급 예정 시각, 지급 시각 |
| payout | `payout_seller` | 판매자 ID와 회원 ID 복제본. 지급할 때 판매자 지갑을 찾는 데 쓴다. |
| wallet | `wallet` | 지갑과 잔액. 플랫폼 지갑도 이 테이블의 한 행이다. |
| wallet | `holding` | 구매자별 보관 금액과 환불 누적액, 상태(`RESERVED`, `SETTLED`, `CANCELED`) |
| wallet | `holding_settlement` | 어느 정산이 어느 홀딩에서 얼마를 꺼냈는지 기록 (홀딩 x 정산 단위) |
| wallet | `wallet_transaction` | 지갑 거래 내역(`SETTLEMENT`: 판매자 입금, `FEE`: 플랫폼 수수료 입금 등) |
| batch | `BATCH_*` (9개) | 스프링 배치 실행 이력 (Job 실행 날짜, 상태, 건너뛴 건수 등) |

홀딩의 남은 금액은 `holding.amount - holding.refundedAmount - holding_settlement 합계`입니다. 정산으로 꺼낸 합계는 별도 테이블에 있어서 환불할 때도 이 값을 반영합니다.

## 6. 상태

**정산 (`PayoutStatus`)**
- `PENDING`: 구매확정되어 정산이 만들어진 상태 (아직 지급 전)
- `COMPLETED`: 지급 완료
- `CANCELED`, `FAILED`: 값은 정의돼 있지만 **아직 쓰이지 않는다.** 입금에 실패한 정산은 `FAILED`가 아니라 `PENDING`으로 남아 다음 날 재시도된다.

**홀딩 (`HoldingStatus`)**
- `RESERVED`: 결제되어 묶여 있음
- `SETTLED`: 남은 금액이 모두 정산에 쓰임 (일부 환불 후 나머지가 정산된 경우 포함)
- `CANCELED`: 정산 없이 전액 환불됨

## 7. 배치 (Spring Batch)

- **실행 시각**: 매일 00:10. 설정 `custom.payout.cron`으로 바꿀 수 있다. (기본값 `0 10 0 * * *`)
- **처리 대상**: `PENDING`이고 지급 예정 시각이 지난 정산. 지급 예정일이 15일이라 **15일에 처음 지급**되고, 실패한 건은 다음 날 다시 대상이 된다.
- **한 건씩 처리**: 청크 크기 1. 한 건이 실패해도 건너뛰고 나머지를 계속 처리한다. 실패 로그는 `PayoutSkipListener`가 남긴다.
- **중복 실행 방지**: Job 파라미터에 실행 날짜(`runDate`)를 넣어서, 같은 날 이미 완료된 Job은 다시 실행되지 않는다.
- **동시 지급 방지**: 정산 행을 락 조회(`PESSIMISTIC_WRITE`)하고, 이미 `PENDING`이 아니면 건너뛴다.

## 8. 중복 처리와 실패 대응

| 상황 | 동작 |
|---|---|
| 같은 구매확정 이벤트가 다시 옴 | 이미 정산이 있는 `order_item_id`는 건너뜀 (유니크 제약도 있음) |
| 같은 정산을 wallet에 다시 요청 | `holding_settlement`에 정산 ID 기록이 있으면 아무것도 바꾸지 않고 종료 (금액이 다르면 예외) |
| 판매자 복제가 없음 | 예외 → 정산은 `PENDING`으로 남고 건너뜀. 복제가 생기면 다음 실행에서 지급 |
| 홀딩의 남은 금액이 모자람 | 예외 → 정산은 `PENDING`으로 남음 (예: 확정 전에 환불이 많았던 경우) |
| 같은 지갑에 입금이 동시에 들어옴 | 지갑 낙관적 락 충돌로 한쪽 실패 → 다음 실행에서 재시도 (배치는 순차 처리라 평소에는 없음) |

## 9. 모듈 경계 (분리 대비)

payout과 wallet은 서로의 클래스를 직접 알지 않고 `shared`의 계약으로만 만납니다.

```
payout ──▶ shared.wallet.WalletSettlementPort (인터페이스)  ◀── wallet.WalletSettlementPortAdapter (구현)
           shared.wallet.dto.SettleAndDepositRequest
```

- 서비스를 분리할 때는 포트 구현체만 HTTP 클라이언트로 바꾸면 됩니다. wallet 정산 처리가 정산 ID 기준 멱등이라, 호출이 실패해도 다음 배치가 다시 호출하면 안전합니다.
- 구매확정 → 정산 생성은 지금 동기 이벤트라 같은 트랜잭션입니다. 분리하면 비동기가 되므로 유실을 막는 보정 장치(재발행 또는 보정 배치)가 필요합니다.

## 10. 설정값

| 설정 | 기본값 | 설명 |
|---|---|---|
| `custom.wallet.platform-member-id` (환경변수 `PLATFORM_MEMBER_ID`) | `1` | 수수료를 받는 관리자 회원 ID. **환경마다 실제 관리자 회원 ID로 맞춰야 한다.** |
| `custom.payout.cron` | `0 10 0 * * *` | 지급 배치 실행 시각 |
| `spring.batch.job.enabled` | `false` | 앱 시작 시 Job 자동 실행 끔 (스케줄러가 실행) |
| `spring.batch.jdbc.initialize-schema` | `always` | MySQL에 배치 메타데이터 테이블 생성 |

코드 상수: 수수료율 3%(`FEE_RATE_PERCENT`), 지급일 15일(`PAYOUT_DAY_OF_MONTH`)은 `Payout.java`에 있습니다.

## 11. 알려진 한계

- 정산은 확정 시점의 금액으로 만들어지므로, **확정 전에 환불된 상품도 정산이 생성**됩니다. 이 경우 홀딩에서 꺼낼 금액이 부족해 지급이 실패하고 `PENDING`으로 계속 남습니다. (정산 생성 시 환불 반영은 아직 구현 전)
- 구매확정 **이후**의 반품·환불은 이미 만든 정산에 반영하는 로직이 없습니다.
- 수수료가 쌓이는 곳은 관리자 회원의 지갑이라 별도의 "플랫폼 수익" 도메인은 없습니다. 수수료 통계는 `FEE` 거래 내역이나 `payout.fee_amount`를 집계해야 합니다.
- 실제 은행 송금 연동은 없고, 지금은 지갑(예치금) 잔액 입금까지만 합니다. 출금은 기존 출금 기능을 쓰는 것을 전제로 합니다.
- 스프링 배치 Job의 통합 테스트(DB 필요)는 저장소에 없습니다. 로컬 MySQL에서 전체 흐름을 한 번 실행해 확인했을 뿐입니다.
