# 관리자 OTP — 설계와 운영 절차

관리자 계정은 **OTP(TOTP) 필수**다. 인증 수단을 추가하면 공격자는 OTP를 깨는 대신 **등록·변경·복구 절차**를 노리므로, 그 길을 먼저 막도록 설계했다.

## 구현된 것

| 규칙 | 구현 |
|---|---|
| 관리자 API는 OTP를 거친 토큰만 | JWT `amr`에 `otp`가 있어야 `ROLE_ADMIN`. 아니면 `ROLE_ADMIN_PENDING` → `/api/admin/**` 403 (`JwtAuthenticationFilter`, 모든 서비스) |
| 인증 방식은 서버가 정한다 | 로그인 시 DB의 역할·OTP 상태로 결정. 관리자에게 이메일 2차 인증 경로 없음 (OTP 미등록일 때 등록 전용 세션만) |
| 등록 가로채기 방지 | OTP 등록은 **비밀번호 + 관리자 메일 코드**를 거친 세션(`amr`에 `email`)에서만 시작·완료. 첫 코드를 맞혀야 활성화 |
| 이미 등록된 OTP | API로 바꾸거나 지울 수 없음 → Break-glass뿐 |
| 비밀키 | AES-256-GCM 암호화 저장 (`MFA_OTP_ENCRYPTION_KEY`) |
| 재사용 방지 | 마지막으로 성공한 30초 구간 번호 저장, 같거나 이전 구간 코드 거부 (조건부 UPDATE). 등록에 쓴 코드도 로그인에 못 씀 |
| 백업 코드 | 10개, 12자(60비트), HMAC 해시 저장, 쓰는 순간 삭제(동시에 써도 한 번) |
| 시도 제한 | challenge당 5번, 계정당 1시간 10번 (이메일 2차 인증과 같은 카운터) |
| 알림·기록 | 등록·백업 코드 사용 시 관리자 메일로 알림 (**커밋된 뒤에만** 보냄), `[보안]` 로그 |
| 비밀번호 변경 | OTP를 해제하지 않음 (세션·신뢰 기기만 폐기) |

## 관리자 세션

관리자는 **업무 세션 하나에 OTP 한 번**이다. 세션이 끝나면 다시 비밀번호 + OTP로 로그인한다.

| 항목 | 일반 회원 | 관리자 |
|---|---|---|
| Access Token | 30분 | **15분** (`custom.jwt.adminAccessTokenExpireSeconds`), 세션 끝 시각을 넘지 않음 |
| 세션(Refresh Token) | 24시간, 로그인 유지 시 30일. 재발급할 때마다 새 수명 | **OTP 확인 시각부터 8시간 고정** (`custom.jwt.adminSessionHours`) |
| 재발급 | 수명이 다시 늘어남 | **끝 시각이 그대로** → 8시간이 지나면 재발급 실패(401) → 다시 OTP |
| 로그인 유지 | 선택 가능 | **없음** (선택해도 무시, 쿠키는 브라우저를 닫으면 사라짐) |
| 신뢰 기기 | 30일 생략 가능 | **없음** (매번 OTP) |

- 재발급은 처음 로그인 때 거친 인증 수단(`amr`)을 그대로 이어 받는다 → OTP 없이 시작한 세션이 재발급으로 OTP 세션이 될 수 없다.
- OTP 등록을 마치면 다른 기기의 세션을 모두 끊고, OTP를 거친 새 세션(8시간)을 준다.
- OTP 등록 전 세션(비밀번호 + 메일 코드)도 관리자 세션이라 8시간 고정이지만, 관리자 API는 403이고 OTP 등록만 할 수 있다.

## 운영 절차 (아직 기능으로 만들지 않은 것)

### 휴대폰 교체
백업 코드로 로그인 → 운영 책임자에게 Break-glass 재등록 요청 (기기 변경 화면은 아직 없음).

### Break-glass: OTP·백업 코드를 모두 잃었을 때

**이메일만으로 OTP를 초기화하지 않는다.** 메일함과 관리자 계정이 함께 털린 상황일 수 있다.

1. 관리자가 OTP 분실을 신고한다.
2. 운영 책임자가 **메일·채팅이 아닌 경로**(대면, 화상)로 본인을 확인한다.
3. **두 사람**(운영 책임자 + 다른 팀원)이 함께 운영 DB에서 아래를 실행한다.
4. 다음 로그인에서 해당 관리자는 비밀번호 + 메일 코드 → **새 OTP 등록**을 거친다.
5. 실행 기록(누가·언제·왜·본인 확인 방법)을 팀 채널에 남기고 **모든 관리자에게 알린다**.

```sql
-- 대상 관리자 회원 ID를 :member_id 에 넣는다. 한 트랜잭션으로 실행
START TRANSACTION;
DELETE FROM member_otp WHERE member_id = :member_id;          -- OTP 비밀키
DELETE FROM member_backup_code WHERE member_id = :member_id;  -- 백업 코드
DELETE FROM refresh_token WHERE member_id = :member_id;       -- 모든 세션
COMMIT;
```

남아 있는 Access Token은 최대 15분 뒤 만료된다.

### 키를 바꿀 때 주의
- `MFA_OTP_ENCRYPTION_KEY`를 바꾸면 기존 OTP 비밀키를 풀 수 없다 → 모든 관리자가 Break-glass 재등록을 해야 한다 (`v1:` 접두사는 나중에 키 교체를 지원하려고 둔 자리).
- 백업 코드 해시는 `MFA_CODE_SECRET`(인증 코드 HMAC 키)을 쓴다 → 이 값을 바꾸면 기존 백업 코드가 모두 무효가 된다.

### 관리자 추가 (현재 정책)
관리자는 운영 책임자가 직접 만든다. 기능화할 때의 설계:
- 기존 관리자가 요청 → **다른 관리자가 승인**(승인자는 OTP 재확인) → 초대한 이메일에만 묶인 일회용 등록 링크(24시간, 해시 저장)
- 링크는 **등록 절차를 시작할 권한만** 준다. 관리자 권한은 비밀번호 설정 + 메일 코드 + **첫 OTP 확인 후** 활성화
- 활성화되면 모든 관리자에게 알림

### 다른 관리자의 OTP 초기화
**지원하지 않는다.** 관리자 계정 하나가 털렸을 때 다른 관리자의 OTP를 벗기는 길이 되기 때문이다. 복구는 Break-glass만.
